Documentation

The playground is a small fake application used across the accessibility series. It exists in two versions that look the same: the accessible version is the reference, and the seeded version has deliberate bugs to find. Nothing you enter in either is saved, and reloading restores the bugs.

Each session below lists what the facilitator covers and the mission participants get. Sessions are filled in as the series goes along.

Sessions

Session 2: ARIA, the accessibility tree, and name, role, value

Goal: see how the browser turns markup into what assistive technology reads, and learn three ways to check it.

Agenda

  1. ARIA. What it is and what it is not. The first rule: no ARIA is better than bad ARIA. Native HTML first, ARIA only to fill the gaps.
  2. DOM versus accessibility tree. The browser builds a second tree from the DOM, the CSS and the ARIA attributes. Screen readers read that tree, not the DOM.
  3. Name, role, value. What each one is, where the name comes from, and how Chrome shows the computation in the Accessibility pane of the Elements panel.
  4. Demo: axe DevTools. Run it on the seeded version and read one result together: the rule, the element, the fix.
  5. Demo: bookmarklets. Two bookmarklets, one that outlines headings and landmarks and one that shows accessible names. Suggestions are in the links below.
  6. Mission. Participants find bugs on the Agents page, in this order: axe, then keyboard, then the trees.
  7. Debrief. What did each method find that the others missed? Decide what session 3 covers.

Mission: find the bugs on the Agents page

Use the seeded version. Stay on the Agents page: the list in Card view and in List view, and the page you reach by opening one agent. Leave the New agent form alone. It belongs to a later session.

For each finding, write down where it is, what is wrong, how you found it, and the WCAG success criterion if you know it.

Part 1: axe DevTools
  1. Open the Agents page and run a full scan. Note each issue, where it is, and what axe says about it.
  2. Switch to List view and scan again. What is new?
  3. Run the same two scans on the accessible version. What remains, and why?
Part 2: keyboard
  1. Reload the seeded Agents page and press Tab until you reach the end of the page. Write down the order of the focus stops. Could you always see where the focus was?
  2. Operate each control with the keyboard only: the Card and List toggle, the search box, a sort header and a row in List view, and the More actions menu on a card. Which ones work, which do not, and which work but tell you nothing about their state?
  3. Open one agent with the keyboard. Where does focus land, what does the browser tab say, and how do you get back?
Part 3: DOM and accessibility tree
  1. In Chrome DevTools, select an element and open the Accessibility pane. Inspect the logo, every control in the top bar and in the toolbar, one card, and one table row. Read off the name, the role and the state of each.
  2. Do the same on the accessible version and compare. Where does the tree differ from what you see on screen?
  3. Pick two of those differences. Which markup is responsible, and how would you fix it?

You may get stuck without a mouse. That is a finding, not a fault of the playground: note where it happened, use the mouse to continue, and carry on.

Session 3: Where am I? Page title, headings, landmarks and language

Goal: give a screen reader user and a keyboard user the same skim you get from the layout, through the page title, the landmarks, the headings, the skip link and the declared language.

Agenda

  1. Skimming. How a sighted user skims a screen by its layout and then by the headings, and what a screen reader uses instead: the page title, the landmarks and the heading outline. A keyboard user skims with the skip link. The declared language picks the voice.
  2. Demo: the home page. The accessible home page with NVDA: the title, the elements list, and the H, D and K keys. Then the same page through the bookmarklets and ANDI.
  3. Mission. Participants find structure bugs on the Settings page in three passes: eyes, x-ray, fix and compare.
  4. What we found together. What each tool showed, what only a screen reader showed, and what nothing found.
  5. The criteria so far. The success criteria touched in Sessions 1 to 3.

Mission: find the structure bugs on the Settings page

Use the seeded version. Stay on the Settings page. It only displays information, so you are looking at how the page is put together, not at what it says.

For each finding, write down where it is, what is wrong, how you found it, and the WCAG success criterion you think it fails.

Pass 1: skim with your eyes
  1. Open the Settings page of the seeded version and look at it for ten seconds.
  2. Write down the outline you expect: the page heading and its sections, in order.
Pass 2: x-ray
  1. Run the Page Title, Headings, Landmarks, Lang and Iframes bookmarklets, then ANDI's Structures and Links modules, then axe with "Best practices" switched on.
  2. Compare each result with your outline and note every gap, with the criterion you think it fails.
  3. Open the browser tab list and the elements list a screen reader user would see. Could you tell where you are?
Pass 3: fix and compare
  1. In your own DevTools, fix three things so that the Headings and Landmarks overlays match your outline.
  2. Open the accessible version and compare the outline, the landmark list and the title.

Fixing more than three is not the point; seeing the outline change is.
